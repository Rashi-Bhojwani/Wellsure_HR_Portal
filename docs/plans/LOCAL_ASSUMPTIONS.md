# Things built locally that assume a local environment

Started 2026-10-16, when the user paused Phase 1.5 (commits B to F) until after Phase 7: all AWS work, the migration and connecting
the device come last, together, as the final stage. Phases 6 and 7 are built and tested **locally**, so anything that quietly depends on
the laptop, the CI runner or a single process is recorded here **as it is written**, not found on the first deploy.

How to use it: add a row the moment you write something that works locally for a reason that will not hold on AWS. The final stage
walks this list top to bottom before the first `cdk deploy`. "Checked" is filled in then, with the date and what was seen.

| # | Assumption (what works locally) | Introduced | What is different on AWS | What to do or verify in the final stage | Checked |
|---|---|---|---|---|---|
| 1 | Postgres and Redis have no TLS and (Redis) no password; the app talks plain `redis://` and `postgresql://` | Phase 0 | RDS and ElastiCache are reached over TLS with an auth token. The production guard already **requires** `sslmode=require` and `rediss://` with a token | The first deploy proves ioredis and Prisma connect and verify certificates; the RDS CA bundle may need to be in the image (`DEPLOYMENT.md`, "To verify on the first deploy") | ☐ |
| 2 | Field encryption uses one static key derived from `KMS_FIELD_KEY_ID` (`FIELD_ENCRYPTION_DRIVER=local`) | Phase 1 | KMS wraps the data keys; `kms:GenerateDataKey` and `kms:Decrypt` with an encryption context are real calls | First deploy: `admin:preflight` encryption round trip; rehearse the rotation procedure once on staging before real data is in it | ☐ |
| 3 | Uploaded files, letter PDFs and (Phase 6) **payslip PDFs and bank files** are written under `.storage/` through `StorageService`; "signed URLs" are simulated by a dev route | Phase 1 | S3 with real presigned URLs, private bucket, KMS encryption at rest, lifecycle rules | Payslip and bank-file objects must be written through `StorageService` only (never `fs`); check the S3 key layout, expiry, and that a payslip URL cannot be guessed or shared past its expiry | ☐ |
| 4 | Mail is written to `.mail/` as `.eml` files and the console (`MAIL_DRIVER=console`) | Phase 1 | SES: verified identity, sandbox until production access, bounces and complaints, sending rate limits | Payslip-published emails (up to the whole headcount at once) must be **paced** like invitations; they must not carry the payslip or any figure, only a link to sign in | ☐ |
| 5 | PDFs (letters, and payslips in Phase 6) are rendered by a Chromium found on the machine | Phase 5 | The image installs Chromium and runs as root with the sandbox off (Phase 5.5 hardening item); ECS task memory limits apply, and a payslip run renders hundreds of PDFs | Measure memory and time for a full-headcount payslip render on the real task size; render in the worker, in bounded batches, never in the API process | ☐ |
| 6 | One API process, one worker, one scheduler on one machine; jobs never run twice | Phase 0 | Several API tasks behind a load balancer, rolling deploys, a worker that is stopped mid-job (SIGTERM, up to the stop timeout) | Every payroll job (calculate, publish, bank file) must be **idempotent and resumable**, keyed in the database, and must survive a worker restart mid-run; the scheduler must stay a single instance | ☐ |
| 7 | The clock is the machine's, in `Asia/Kolkata` (`businessToday()`); tests can set it | Phase 2 | Containers run in UTC; every date decision already goes through `businessToday()` | Confirm no payroll code calls `new Date()` for a business date; the weekly clock audit already runs the suite at five instants | ☐ |
| 8 | Local development runs the app as one all-powerful database role; tests purge append-only tables through a development-only exception | Phase 5 | The app role cannot UPDATE/DELETE append-only tables (Phase 1.5 commit A) | New payroll append-only tables are covered automatically (the migrate step finds them from their triggers); check the app role can do every legitimate payroll write, by running the payroll walkthrough as the app role once | ☐ |
| 9 | `http://localhost` URLs in emails and cookies; refresh cookie `SameSite=Strict` works because web and API share `localhost` | Phase 1 | Web and API need hostnames under one registrable domain; links in emails must be `https` | Payslip links in notifications and emails are built from `WEB_BASE_URL` only | ☐ |
| 10 | The test suite and a dev server can use the same Postgres and Redis servers; a test lock now stops two test runs sharing one database (Phase 6 housekeeping) | Phase 6 | CI runs one suite per runner against a service container | None, noted so nobody assumes the lock exists in staging | ☐ |
